1. Executive Summary and Problem Statement

1.1 Client Background

FEETrack is an enterprise-grade coaching fee management platform and parent engagement portal designed for large-scale multi-centre coaching institutes. The operational profile modeled by the system reflects:
  • Footprint: 4 branch centres across Jaipur (Jaipur Central, Vaishali Nagar, Malviya Nagar, Mansarovar).
  • Scale: ~2,600 enrolled students across medical (NEET) and engineering (JEE) preparatory batches.
  • Staffing: ~140 faculty members, front-office executives, accountants, and academic counsellors.
  • Financial Volume: Average annual tuition of ₹1.2 lakh per student, structured across 3–4 scheduled instalments, yielding tens of crores in annual collections.

1.2 Core Operational Deficiencies

Prior to FEETrack, fee operations relied on fragmented spreadsheets, disconnected POS machines, and paper receipts, creating four critical vulnerabilities: 1. Reconciliation Lag: Online bank transfers and UPI remittances frequently arrived with truncated or missing student roll numbers, creating an untracked suspense account queue exceeding lakhs of rupees. 2. Cash Leakage & Delayed Receipts: Front-desk cash collections required immediate, tamper-evident GST receipts with sequential numbers to prevent administrative fraud. 3. Dropout & Default Blindspots: Student withdrawals frequently correlated with early fee arrears, unexplained attendance declines, and deteriorating test scores. Counsellors lacked a unified triage desk to detect dropouts prior to departure. 4. Disputed Withdrawal Settlements: When students withdrew mid-session, subjective manual refund calculations triggered contentious disputes. An auditable, pro-rata refund desk with statutory GST deductions and rigid departure deadlines was needed.

1.3 System Solution

FEETrack resolves these operational bottlenecks through:
  • A high-security, bilingual (English & Hindi) Parent Portal enabling instant fee ledger review, online payments, and GST receipt downloads.
  • A desktop-optimized Accounts Desk offering multi-centre aggregation, offline payment recording, unmatched payment reconciliation, atomic pro-rata refund processing, and automated fee reminders.
  • A multi-signal Dropout-Risk Triage Engine operating under strict pastoral decoupling (academic intervention without financial penalties).

2.1 Project Scope

The system encompasses end-to-end fee lifecycle management, parent mobile engagement, and operational compliance.

2.2 System Goals

  • Financial Precision: Absolute elimination of IEEE-754 floating-point errors by storing and computing all monetary values in integer paise (1\text{ INR} = 100\text{ paise}).
  • Concurrency Safety: Guaranteeing that simultaneous payout or rejection requests on a refund record cannot result in duplicate payouts or overwritten audits.
  • Zero Client-Side Token Footprint: Elimination of JWT exposure to XSS attacks by avoiding browser localStorage and sessionStorage.
  • Bilingual Accessibility: Complete English and Hindi parity across all UI elements, status labels, and SMS/WhatsApp reminder templates.

2.3 Non-Goals (Explicit Exclusions)

  • Live Monetary Processing: This version does not connect to live banking networks or live payment aggregator credentials (runs on a verified MockPaymentGateway).
  • Live Telecom Dispatch: Does not send real-world SMS or WhatsApp messages (runs on a verified MockMessageProvider logging to MessageLog).
  • Real-Time Financial Penalties: The dropout-risk engine is strictly decoupled from financial operations; it does not block students, assess late fines, or send automated debt collection demands.
  • Enterprise ERP / LMS: Does not provide timetable scheduling, online video classes, or human resource payroll management.

4.2 Key Architectural Decisions

Decision 1: Pure Domain Layer Decoupling

Business logic is decoupled into pure JavaScript functions in server/src/domain/:
  • instalment.js: Derives instalment status (paid, part_paid, overdue, due_soon, upcoming) and overdue days.
  • payment-allocation.js: Computes FIFO and targeted credit allocations.
  • refund.js: Computes pro-rata refunds, statutory GST splits, and deadline enforcement.
  • risk-scorer.js: Computes multi-signal weighted dropout scores.
*Rationale:* Domain pure functions take plain objects, return plain objects, and possess zero database or Express dependencies, enabling instantaneous unit testing and provable determinism.

Decision 2: HttpOnly Cookie Sessions over Bearer Tokens

Instead of storing JWTs in localStorage (vulnerable to XSS extraction), authentication issues an httpOnly, SameSite=Lax, Secure cookie named fee_portal_session. All API requests enforce credentials: 'include'.

Decision 3: Atomic Status Transitions for Financial Operations

To prevent race conditions during refund payouts, status transitions utilize atomic database modifications: 
const updatedRefund = await Refund.findOneAndUpdate(
  { _id: refundId, status: 'confirmed' },
  { $set: { status: 'paid', payout: payoutData } },
  { new: true }
);
if (!updatedRefund) {
  return res.status(400).json({ error: 'Refund has already been processed or is not in confirmed state' });
}

7. Authentication, Authorization and Security

7.1 Cookie Lifecycle & Cross-Origin Security

  • Cookie Flags: httpOnly: true, secure: process.env.NODE_ENV === 'production', sameSite: 'lax', maxAge: 28800000 (8 hours), path: '/'.
  • Domain Scoping: Configured via optional COOKIE_DOMAIN. When set (e.g. COOKIE_DOMAIN=.feetrack.in), both portal.feetrack.in and api.feetrack.in share the cookie across same-site subdomains. When omitted, host-only scoping applies.
  • CORS Allowlisting: cors({ origin: env.CLIENT_ORIGIN, credentials: true }). Wildcards are prohibited.

7.3 OWASP Security Implementations

1. CSV Formula Injection Mitigation: All CSV report exports run through server/src/utils/csvSanitizer.js. Any cell beginning with =, +, -, @, \t, or \r (even after stripping leading whitespace) is prepended with a single quotation mark ('). 2. Webhook Timing-Attack Defense: Webhook verification compares the computed HMAC-SHA256 digest against the header signature using crypto.timingSafeEqual(Buffer.from(sig), Buffer.from(expectedSig)). 3. Rate Limiting: OTP generation is throttled to 5 requests per 60-second window per client IP/phone using express-rate-limit.

8. Main End-to-End Workflows

8.1 Parent Login and Fee Viewing Workflow

1. Parent enters phone number (+919900000041) at /login. 2. Backend validates E.164 phone regex, generates a 6-digit OTP, stores it in memory with a 5-minute TTL, and dispatches via otpProvider. 3. Parent submits OTP. Backend validates code, signs a 24-hour JWT containing { sub: user._id, role: user.role }, and sets fee_portal_session cookie. 4. Client hydrates session via GET /api/auth/me. If first login, the Consent Modal is presented (POST /api/auth/consent). 5. Client requests GET /api/parent/children. Backend queries Student.find({ parentUserId: req.user._id }), derives instalment statuses, and returns child cards.

8.2 Payment and Webhook Processing Workflow

Figure 4: Parent Payment and Webhook Allocation Sequence

8.3 Receipt Generation Workflow

1. Triggered immediately upon payment confirmation (online webhook or manual collection). 2. Inclusive GST calculation splits amount (18\% inclusive):
\text{gst} = \text{roundDiv}(\text{amount} \times 18, 118), \quad \text{base} = \text{amount} - \text{gst}
3. Sequence generator atomically executes Counter.findOneAndUpdate({ _id: 'receipt_2026' }, { $inc: { seq: 1 } }, { upsert: true, new: true }). 4. Formats receipt number: RCP-2026- padded with 6 digits (e.g. RCP-2026-000042). 5. Inserts immutable Receipt document linked by unique paymentId.

8.4 Accounts Dashboard and Manual Payment Collection

1. Accounts staff visits /accounts/dashboard. API aggregates total tuition, total collected, overdue arrears, active students, and batch summaries. 2. For an in-person cash/cheque payment, staff selects student, enters amount, payment mode, and reference. 3. Backend runs planPaymentAllocation. If untargeted, credits oldest due instalment first (FIFO). 4. Updates instalment paid balance, generates sequential GST receipt, and returns receipt modal to staff for instant printing.

8.5 Unmatched Payment Handling

1. Bank remittances arriving without valid student references enter Payment with status: 'unmatched' and create an UnmatchedPayment record with status: 'open'. 2. Accounts staff inspects /accounts/unmatched. 3. Staff can either: - Match to Student: Staff searches student roll number; backend executes FIFO credit allocation, marks payment matched, and resolves queue item. - Dismiss: Staff dismisses erroneous or duplicate bank deposits with a mandatory audit reason.

8.6 Refund Processing Workflow

Figure 5: Accounts Refund Calculation and Atomic Payout Sequence

8.7 Fee Reminder Engine Workflow

1. Schedulers trigger daily at 09:00 AM IST (server/src/services/reminderService.js). 2. Schedulers scan active instalments against business date clock.today(). 3. For eligible instalments at offsets T-3, T, T+3, T+7, T+15, verifies if (instalmentId, offsetDays) exists in Reminder. 4. If missing, inserts Reminder { status: 'pending' }. 5. Pre-dispatch check: Immediately re-queries instalment balance. If zero or student withdrew, marks cancelled. 6. Dispatches bilingual template via messageProvider and records timestamp and status to MessageLog.

8.8 AI-Assisted Dropout-Risk Detection & Counsellor Follow-up

1. Schedulers trigger nightly at 02:00 AM (server/src/services/riskService.js). 2. Evaluates all active students across payment delays, attendance drops, and test score drops. 3. If aggregate score \ge 65 (High Risk), checks cooldownUntil date on existing flags. 4. If cooldown expired and no open flag exists, creates RiskFlag { score, band: 'high', reasons, status: 'open' }. 5. Counsellor reviews /accounts/risk, places pastoral check-in call, and updates flag to called or false_flag (triggering 30-day cooldown).

9. AI/Automation Design, Explainability and False-Positive Handling

9.1 Multi-Signal Additive Heuristic

The dropout-risk engine is a transparent, explainable heuristic scoring model operating on a bounded 0 to 100 scale:
\text{RiskScore} = \min\left(100, \text{Score}_{\text{payment}} + \text{Score}_{\text{attendance}} + \text{Score}_{\text{test}}\right)
+-----------------------------------------------------------------------------------+



SIGNAL WEIGHTING BREAKDOWN (Max 100 Points)


1. Payment Signals (Max 50 Points):
- Instalment Overdue > 30 Days: +35 points
- Instalment Overdue 15–30 Days: +20 points
- Part-Paid with remaining overdue balance: +15 points
- Historical repeated defaults (>1 overdue instalment): +10 points
2. Attendance Trajectory (Max 30 Points):
- 30-Day Attendance Rate < 60%: +30 points
- 30-Day Attendance Rate 60%–75%: +20 points
- Unexplained consecutive absences (>3 sessions): +10 points
3. Academic Test Performance (Max 20 Points):
- Severe downward trajectory across last 3 tests (>20% drop): +20 points
- Moderate downward trajectory (10%–20% drop): +10 points
- Test absenteeism (missed scheduled internal mock): +10 points

+-----------------------------------------------------------------------------------+

9.2 Explainability Guarantees

The scorer generates human-readable diagnostic strings returned alongside the numeric score:
  • *"Instalment overdue by 23 days with unpaid balance of ₹15,000"*
  • *"30-day attendance dropped to 64% (3 consecutive missed sessions)"*
  • *"Test score trajectory declined by 22% over last 3 mocks"*

9.3 False-Positive Mitigation & 30-Day Cooldown

If a student was flagged due to temporary approved medical leave or sanctioned fee delay: 1. Counsellor marks flag as false_flag and enters explanatory notes (e.g. *"Student hospitalized for jaundice; medical certificate provided"*). 2. The system sets cooldownUntil = clock.today() + 30 days. 3. The nightly risk engine checks student.cooldownUntil. Any automated flag generation for this student is suppressed until the cooldown window elapses.

12. Limitations, Risks and Future Improvements

12.1 Current System Limitations

1. Mock Integrations: Payment links, HMAC webhooks, OTP codes, and WhatsApp reminders run against simulated in-memory adapters. 2. Single-Instance Cron Schedulers: Schedulers execute in-process via node-cron. If backend containers are scaled horizontally without a distributed lock (e.g. Redlock or MongoDB collection lock), reminder evaluations would trigger redundantly. 3. Cross-Site Vendor Cookies: When deployed across different vendor domains (.vercel.app vs .onrender.com), browsers block SameSite=Lax cookies on asynchronous fetch calls unless a shared apex domain (.feetrack.in) is provisioned.

12.2 Risk Register & Mitigations

RiskProbabilitySeverityArchitectural Mitigation
Double Refund PayoutLowHighAtomic findOneAndUpdate({ _id, status: 'confirmed' }) ensures second concurrent request receives HTTP 400.
Duplicate Webhook AllocationsMediumHighSparse unique index on Payment.gatewayRef causes duplicate webhook deliveries to exit idempotently.
Formula Injection in ExcelMediumMediumOWASP CSV sanitizer strips whitespace and prepends ' to dangerous mathematical operators.
Unapproved Policy DisputesHighMediumUI and TDD explicitly label the pro-rata refund formula as an assumed policy pending institute legal sign-off.

12.3 Future Roadmap (Post-Release)

1. Commercial Aggregator Adapter: Implement concrete RazorpayPaymentGateway and CashfreePaymentGateway satisfying the standard interface. 2. DLT-Approved Telecom Adapter: Integrate GupshupMessageProvider or TwilioMessageProvider with Indian telecom DLT template IDs. 3. Distributed Worker Process: Decouple node-cron schedulers from the web API into a dedicated singleton worker service (worker.js).
